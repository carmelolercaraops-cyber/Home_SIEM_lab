# Home SIEM Lab

A personal home lab focused on Security Operations Center (SOC) fundamentals, endpoint telemetry, threat detection, alerting, and security investigation.

The project documents a practical workflow in which controlled security activity is generated in a Windows laboratory environment, telemetry is collected and forwarded to Splunk, detections are developed using SPL, and the resulting alerts and evidence are analyzed from a SOC perspective.

The laboratory is designed as an ongoing project. Additional security simulations, detections, investigations, and analysis workflows may be added over time.

## Project Goals

The main objectives of this lab are:

- Practice endpoint telemetry collection and analysis.
- Understand how security events are generated and represented in logs.
- Develop and test detection logic using Splunk SPL.
- Create and validate real-time security alerts.
- Investigate process execution and parent/child process relationships.
- Correlate different sources of telemetry when available.
- Document the reasoning behind detections and alert classification.
- Produce SOC-style investigation reports based on observed evidence.
- Maintain a reproducible and transparent workflow suitable for a personal SOC learning portfolio.

The project focuses on documenting activities and results that have actually been performed and validated in the laboratory.

## Methodology

The general workflow followed by the project is:

1. Generate controlled security activity inside the Windows laboratory environment.
2. Collect endpoint telemetry using Sysmon and Windows logging facilities.
3. Forward relevant telemetry to Splunk using the Splunk Universal Forwarder.
4. Store the collected events in a dedicated Splunk index.
5. Develop detection logic using Splunk Search Processing Language (SPL).
6. Test the detection logic against the telemetry generated by the laboratory activity.
7. Configure real-time alerts where appropriate.
8. Validate that the alert is actually triggered by the corresponding activity.
9. Investigate the resulting telemetry and relevant process relationships.
10. Document the findings, indicators, detection logic, and recommended actions.
11. Preserve relevant evidence in a sanitized form.
12. Commit the completed analysis and supporting material to this repository.

Each analysis is documented only after the corresponding activity and telemetry have actually been generated and validated.

## Detection and Investigation Approach

Detections are based on observable telemetry rather than assumptions.

Depending on the activity and available telemetry, investigations may consider:

- Process creation events
- Parent and child process relationships
- Command-line information
- User and host context
- Process identifiers
- File hashes
- Windows event identifiers
- PowerShell logging
- Network and DNS telemetry when available
- Correlation between different telemetry sources
- The relationship between observed activity and the intended security technique

A detection is considered validated only when the corresponding laboratory activity has produced observable telemetry and the detection logic has been tested against that telemetry.

Where real-time alerting is used, validation includes the complete workflow from activity generation to telemetry ingestion, detection, and alert triggering.

## Evidence and Sanitization

The repository contains documentation and evidence generated during actual laboratory activities.

Before being published, evidence files are sanitized to avoid exposing unnecessary personal or system-specific information.

Depending on the artifact, sanitization may include replacing:

- Hostnames
- Usernames
- Personal identifiers
- Internal environment details
- Other information that is not necessary to understand the analysis

Sanitized values are used consistently where possible so that relationships between events remain understandable.

Raw logs containing personal, identifying, or otherwise unnecessary system information are not published.

The purpose of sanitization is to preserve the technical value of the evidence while preventing the disclosure of sensitive or personally identifying information.

## Repository Structure

The repository is organized around individual laboratory analyses.

A typical analysis may contain:

    analysis/
    ├── README.md
    ├── detection.spl
    ├── alert.md
    ├── report.md
    └── evidence/
        └── sanitized-log-files

The exact contents may vary depending on the telemetry and investigation performed.

### README.md

Documents the laboratory activity, its purpose, the telemetry involved, and the overall analysis.

### detection.spl

Contains the SPL detection logic used during the analysis.

Detection logic is included when it has actually been developed and tested in the laboratory.

### alert.md

Documents the corresponding Splunk alert configuration and validation when real-time alerting is part of the analysis.

### report.md

Contains the SOC-style investigation report, including the reasoning used to classify and escalate the observed activity.

### evidence/

Contains sanitized evidence produced during the laboratory activity.

## Documentation Principles

### Evidence over claims

Only activities that have actually been performed are documented as completed.

### No fabricated results

Screenshots, logs, detection results, alert results, timestamps, process information, and other technical details are not fabricated.

### Clear distinction between laboratory activity and real incidents

The security activity documented in this repository is intentionally generated for testing purposes.

A confirmed detection therefore represents a successful laboratory detection unless explicitly stated otherwise. It should not be interpreted as evidence of a real-world compromise.

### Reproducibility

Where practical, documentation describes the relevant commands, configuration, telemetry sources, detection logic, and investigation methodology needed to understand how a result was obtained.

### Progressive development

The repository is developed incrementally.

New laboratory activities and analyses are added as they are completed and validated rather than defining the entire final scope in advance.

## SOC Investigation Reports

Where appropriate, investigations follow a consistent structure:

- Time of activity
- Affected entities
- Reason for classifying the event as a true positive
- Reason for escalating the alert
- Recommended remediation actions
- Attack indicators

This structure is used to practice the reasoning and documentation involved in a SOC investigation.

## Scope

This is a controlled personal laboratory.

The security activity documented in this repository is generated intentionally inside the laboratory environment for defensive security research, detection engineering, and SOC learning purposes.

The project does not claim to represent production-scale security operations or a complete enterprise SOC environment.

Its purpose is to demonstrate a practical understanding of the workflow from endpoint activity to telemetry, detection, alerting, investigation, and documented evidence.
